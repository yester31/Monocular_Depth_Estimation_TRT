# 측정 기록 — 무엇을 재서 무엇을 알았나

`PLAN.md` 에서 옮겨 왔다. 계획서는 "다음에 무엇을 하는가" 를 답해야 하는데,
결과가 쌓이면서 881줄이 되어 그 질문에 답하지 못하게 됐다.

**한 줄도 고치거나 지우지 않았다.** 절 순서와 제목은 원래대로다.

각 절은 그 단계가 무엇을 재서 무엇을 알았는지, 그리고 **알아내지 못한 것이
무엇인지** 를 적는다. 마지막 부분이 이 문서의 존재 이유다 — 결론만 남기면
다음 사람이 같은 것을 다시 재게 된다.

| 절 | 알아낸 것 |
| --- | --- |
| 1. P0 측정 메타데이터 | 클럭이 흔들리면 커널 선택이 난수가 된다. 같은 입력의 unik3d 빌드 4회가 19.04 / 13.35 / 8.41 / 14.49 ms |
| 2. P1 공통 전처리 | 13/14 가 바이트 동일. 어려운 곳은 리사이즈가 아니라 **산술 dtype** 이었다. `depth_pro` 는 남겼다 |
| 3. P2 평가 입력 | DIODE 에서 결정적 크롭으로 4:3 · 16:9 · portrait |
| 4. P3 정답 데이터 평가 | 미터에서 갈리는 것은 **보는 능력이 아니라 보정**이다. 같은 정렬을 허용하면 전 모델이 4.4~6.5% 안에 든다 |
| 5. P4 fp16 대 fp32 | **fp16 은 정확도에서 측정되지 않는다.** 두 모델은 fp32 로 빌드 자체가 안 된다 |
| 6. P5 D2·D3 | uint8 은 변이로 채택. **큰 입력이 더 낫지 않다** — 발표 크기를 바꾸지 않는다 |
| 7. P6 빌더 레벨 | 레벨 5 는 `vggt` 를 **2배 느리게** 만들었다(105분 빌드). 더 오래 찾는 것이 더 빠른 것이 아니다 |
| 8. P7 시각화 | metric/relative/scale-unknown 3구역. 3종횡비 라이브 엔진 경로까지 실행 완료 |
| 9. 검증 자체를 검증 | **테스트 240개가 실패할 수 없었다.** 발표 수치 감사에서 불일치 16 묶음 |

## 1. P0 — 측정 메타데이터 완성

### 목적

낡거나 잘못 빌드된 엔진을 일반 벤치마크 결과만 보고도 발견할 수 있게 한다.

### 작업

1. 일반 벤치마크가 끝난 뒤 별도의 짧은 프로파일 구간을 실행한다.
2. 프로파일러는 timed loop에 붙이지 않는다. 레이어 프로파일은 실행을 직렬화하므로
   같은 구간에서 측정하면 발표용 latency가 오염된다.
3. 각 결과 JSON에 다음을 기록한다.
   - `clock_mhz`, `clock_max_mhz`
   - fp32 출력 레이어 시간 비중
   - Reformat/Slice 등 데이터 이동 시간 비중
   - 엔진 레이어 수와 정밀도 구성
4. 이전 JSON을 읽는 코드와 표 생성기는 새 필드가 없더라도 동작하게 한다.

### 완료 조건

- 14개 결과 모두 환경과 프로파일 요약 필드를 가진다. (현재 프로파일 13개 —
  `tr2m` 미생성.)
- 발표용 latency는 프로파일 기능 추가 전후 1% 이내에서 재현된다.
- `tests/test_bench.py`, `tests/test_profiles.py`, `compare.py --check`가 통과한다.

## 2. P1 — 공통 전처리를 실제 경로에 연결

### 결과

유형 대조표는 [`model_contracts.md`](model_contracts.md) "전처리 유형과 산술 dtype" 으로
흡수했다. **코드를 고치기 전에 먼저 썼다.**

| 유형 | 모델 수 |
| --- | ---: |
| stretch | 11 |
| keep-ratio + pad | 1 (`metric3d_v2`) |
| square pad | 2 (`vggt` · `streamvggt`) |

13개 모델이 `core/preprocess.py` 를 쓰고, `np.array_equal` 로
`reports/inputs/<model>.npy` 와 **바이트 동일**하다. 13/13 동일, 0 차이.
`reports/inputs` 에는 한 글자도 쓰지 않았다.

**어려운 곳은 리사이즈가 아니라 산술 dtype 이었다.** `uint8/255.0` 은 float64 로
승격되고, `uint8.astype(f32)/255.0` 은 float32 로 남고, 파이썬 리스트 평균은 다시
float64 로 승격된다. `spec.json` 에 똑같이 `stretch`+`imagenet` 이라고 선언한 6개
모델이 이 경계의 양쪽에 나뉘어 있었다. **선언만 보고는 알 수 없는 차이다** —
이것이 "선언" 과 "구현" 을 대조하는 단계를 먼저 둔 이유다.

### `depth_pro` 는 남겼다 — 중단 조건대로

정규화를 리사이즈보다 먼저 하고 torch bilinear(`align_corners=False`)를 쓴다.
cv2 `INTER_LINEAR` 는 같은 수학인데도 7,077,888 개 중 2,436,611 개(34.4%)에서
최대 `1.788e-07` 차이가 난다. `core/preprocess.py` 가 torch 를 import 하게 만드는
대신 이 모델은 자기 경로에 남겼다.

### 건드리지 않은 것과 그 이유

`run.py` 와 `common.py` 는 **전처리를 하지 않는다** (`run.py` 는 conda 명령을
조립한다). `models/*/infer.py` 는 PyTorch 참조 구현이고 실제로 다르다 —
`moge_2/infer.py` 는 388x518 로 늘이는 대신 INTER_AREA 로 518 까지 비율 유지
리사이즈를 한다. 대조할 기록된 tensor 가 없으므로 전환하지 않았다.

### 원래 계획

### 목적

`core/preprocess.py`를 테스트 전용 코드가 아니라 평가와 시각화가 공유하는 실제
구현으로 만든다. ONNX의 고정 입력 크기나 모델별 수학은 바꾸지 않는다.

### 작업 순서

1. 12개 모델의 현재 전처리 호출부와 `spec.json` 선언을 대조한다.
2. canary 모델을 유형별로 하나씩 선정해 공통 전처리로 연결한다.
   - stretch
   - keep-ratio resize
   - keep-ratio pad
   - square crop/pad
3. 기존 코드와 공통 코드에 같은 uint8 이미지를 넣고 입력 tensor와 geometry를
   비교한다.
4. canary가 통과한 유형부터 같은 유형의 나머지 모델로 확장한다.
5. `run.py infer`와 이후 평가·시각화 경로가 같은 함수를 사용하게 한다.

### 완료 조건

- 12개 모델 모두 전처리 유형을 `spec.json`에서 결정한다.
- **`reports/inputs/<model>.npy` 가 바이트 단위로 동일하다.** 허용오차가 아니다.
  이 파일은 `verify_accuracy.py` 가 엔진과 ONNX 를 비교할 때 쓰는 기준 입력이라,
  여기가 조금이라도 움직이면 12개 정확도 기준선이 전부 소리 없이 이동하고 이후
  비교가 무엇과의 비교인지 알 수 없게 된다. 같은 수학이므로 바이트 동일이
  가능하고, 안 되면 그건 전처리가 실제로 바뀐 것이다.
- 좌표 복원(resize/pad 역변환)이 기존과 일치한다.
- 4:3, 16:9, 정사각형 입력 테스트가 통과한다.
- `tests/test_preprocess.py`가 표준 테스트 실행에 포함되거나, 선택 의존성 누락 시
  명시적으로 skip한다.
- 기존 ONNX·엔진·발표용 벤치마크는 바뀌지 않는다.

### 중단 조건

한 모델이라도 입력 tensor 또는 좌표 계약이 달라지면 전체 일괄 전환을 멈추고 그
모델을 기존 경로에 남긴다. 차이를 “사소한 전처리 변경”으로 간주하지 않는다.

## 3. P2 — 평가 입력 세트 확장

### 결과

`data/eval/aspects.json` — manifest 는 `tools/prepare_eval_inputs.py` 가 만든다.
손으로 쓰지 않는다(규칙 7). 로더는 `core/eval_inputs.py`, sha256 을 검증한다.

| 종횡비 | 해상도 | 원본 DIODE 프레임 |
| --- | --- | --- |
| 4:3 | 1024x768 (무크롭) | `scene_00019/scan_00183` |
| 16:9 | 1024x576 | `scene_00020/scan_00186` |
| portrait | 576x768 | `scene_00021/scan_00192` |

**D1 은 "이미 있는 것을 쓴다" 로 닫았다.** 새 이미지를 받지 않고 라이선스·출처가
확인된 DIODE 실내 프레임에서 결정적 중앙 크롭으로 만들었다. manifest 에 원본
파일명·원본 크기·크롭 좌표·sha256 이 들어가므로 재현 가능하다.

라이선스는 MIT (`https://diode-dataset.org/`, 2026-08-13 확인). 이 문구는
`tools/make_eval_manifest.py` 가 이미 인용하던 것을 그대로 재사용했고 **독립
재확인은 하지 않았다.**

`demo.py` 가 이 세 종횡비를 실제로 읽어 그린다(P7 참조).

### 원래 계획

### 필요한 결정 D1

평가 이미지를 사용자가 제공할지, 라이선스가 명확한 외부 데이터에서 가져올지
정해야 한다. 출처를 확인할 수 없는 이미지는 저장소에 추가하지 않는다.

### 최소 입력 구성

| 유형 | 최소 수량 | 용도 |
| --- | ---: | --- |
| 4:3 landscape | 1 | 현재 MoGe/Metric Anything 기준 유지 |
| 16:9 landscape | 1 | 종횡비 변화 검증 |
| portrait 또는 near-square | 1 | pad/resize 좌표 검증 |
| 실내 정답 깊이 | 1 scene 이상 | metric 품질 평가 |

각 입력에는 출처, 라이선스, 원본 크기, SHA-256을 manifest로 기록한다.

### 완료 조건

- 최소 세 종횡비가 자동 테스트와 시각화에 사용된다.
- 모든 파일의 사용 권한과 출처가 문서화된다.
- 테스트 입력과 정답 데이터는 별도 manifest에서 구분된다.

## 4. P3 — 정답 데이터 평가 체계

### 결과

`reports/gt.md`. DIODE 실내 50장, 미터, z-depth, 스캐너 마스크 적용.

| 모델 | 정렬 | AbsRel | δ1 | 원하는 배율 |
| --- | --- | ---: | ---: | ---: |
| `depth_anything_ac` | scale+shift | 5.44% | 96.6% | — |
| `distill_any_depth` | scale+shift | 5.96% | 95.9% | — |
| `zipdepth` | scale+shift | 7.93% | 93.3% | — |
| `metric3d_v2` | none | 13.10% | 86.6% | 1.000 |
| `metric_anything` | none | 15.63% | 75.4% | 1.123 |
| `depth_pro` | none | 17.48% | 72.7% | 1.012 |
| `unidepth_v2` | none | 18.22% | 67.8% | 1.081 |
| `moge_2` | none | 21.39% | 52.1% | 1.192 |
| `unik3d` | none | 22.42% | 56.1% | 1.146 |
| `depth_anything_v2` | none | 23.06% | 52.0% | 1.141 |
| `depth_anything_v3` | none | 60.87% | 0.2% | 2.609 |

**위아래는 순위가 아니다.** 위 3개는 자기가 주장하는 만큼(scale+shift)을 맞춘 뒤,
아래는 나온 미터 그대로 채점했다. 세로로 읽는 것이 이 표가 유도하는 유일한 오독이라
정렬 방식을 표 안에 넣었다.

**마지막 열은 진단이지 점수가 아니다.** 모두에게 같은 정렬을 허용했을 때 전 모델이
4.4%~6.5% 안에 들어온다. 미터에서 갈리는 것은 보는 능력이 아니라 보정이다.
`depth_anything_v3` 의 2.609 만 품질이 아니라 단위 문제다.

**채점되지 않은 3개:** `vggt` · `streamvggt` 는 출력이 정규화 좌표계라
(장면 점들의 평균 거리 = 1, 논문 본문 확인) metric 순위에 넣지 않는다 — scale 정렬로는
평가 가능하며 P1 뒤에 별도 표로 낸다. `tr2m` 은 프롬프트가 이미지마다 필요해 평가
계약이 다르다.

### `metric3d_v2` 의 clip 순서가 업스트림과 다르다 (2026-08-14, 발표 수치 영향 없음)

`tools/evaluate_gt.py:176` 은 de-canonical 곱셈 **전에** 자른다:

```python
return np.clip(d, 0, 300) * (fx * scale / 1000.0)
```

업스트림 Metric3D 는 곱한 **뒤** 미터를 clamp 한다:

```python
pred_depth = pred_depth * canonical_to_real_scale
pred_depth = torch.clamp(pred_depth, 0, 300)
```

canonical 을 300 에서 자르고 `0.7113` 을 곱하면 실효 상한이 **300 m 가 아니라
213.4 m** 가 된다.

**발표된 수치는 바뀌지 않는다.** DIODE 실내는 17 m, 실외도 78 m 근처라 두 상한
모두 훨씬 위다. 그래도 기록하는 이유는 **두 순서가 같은 연산이 아니고**, 실제로
먼 깊이가 있는 데이터셋에서는 차이가 드러나기 때문이다.

### `metric3d_v2` 의 spec 은 두 계층을 말한다

`spec.json` 이 `"depth_scale": "metric"` 이라고 하면서 출력 의미는
`"canonical depth — NOT metres, see D12"` 라고 한다. **둘 다 맞다.** 엔진 출력이
canonical 이고, `evaluate_gt.py` 의 어댑터가 manifest 의 초점거리를 넣어 미터로
만든다. 계층이 다를 뿐 모순이 아니다.

기록해 두는 이유는 실제로 이것을 모순으로 읽고 한 절을 쓴 조사가 있었기 때문이다.

### `vggt` · `streamvggt` — 채점 준비는 끝났다, 실행만 남았다 (2026-08-14)

- 두 어댑터가 `evaluate_gt.py` 에 들어갔고 `reports/inputs/*.npy` 대비
  **max|diff| = 0.000e+00** 로 바이트 일치한다.
- `core/gt.py` 에 `scale_only()` · `policy_for_normalised()` 를 **기존
  `align`/`metrics` 를 건드리지 않고** 추가했다. 발표된 11개 점수가 그 함수들 위에
  서 있기 때문이다.
- `--scale-only` 는 `reports/gt_scale_only.md` 에만 쓴다. `reports/gt.md` 는
  덮어쓰지 않는다.
- 검증 두 단계: 합성 정규화 좌표에서 정규화 상수 `c` 를 rel `1e-12` 로 복원했고,
  가짜 엔진으로 `score_model` 전 경로를 돌려 심어둔 배율 3.7 을 3.7009 로
  복원했다(패드/리사이즈 왕복 오차 0.024%).
- 그 과정에서 **NaN 픽셀 하나가 scale 적합 전체를 오염시키는 결함**을 찾아
  `--scale-only` 경로에서만 마스크를 좁혀 고쳤다.

**실행은 데스크탑이 필요하다** — 이 노트북에는 엔진도 DIODE 도 없다.

`tr2m` 평가 계약은 [`model_contracts.md`](model_contracts.md) "`tr2m` 평가 계약" 에 있다.

### 원래 계획

### 목적

현재 가장 큰 위험인 “속도는 빨라졌지만 품질 손실을 모른다”를 닫는다.

### 데이터 계약

평가 manifest는 최소한 다음 정보를 가진다.

- RGB 경로와 원본 크기
- depth 경로, 단위, invalid 값
- valid mask
- 카메라 intrinsics가 있으면 그 값과 좌표계
- 평가 crop/resize 규칙

### 출력별 평가 규칙

| 출력 계약 | 평가 방식 |
| --- | --- |
| metric depth | 스케일 정렬 없이 AbsRel, RMSE, δ1 |
| relative depth | 정렬 전 결과와 명시된 scale/shift 정렬 후 결과를 분리 보고 |
| canonical/point map | 해당 모델 계약에 맞는 변환 후 평가; 변환을 못 검증하면 순위 제외 |
| VGGT/StreamVGGT geometry | 출력 의미가 확정되기 전 metric 순위에 넣지 않음 |

### 완료 조건

- 같은 이미지·mask·평가 해상도로 14개 모델을 실행한다. (현재 11개 채점 +
  3개 명시적 미채점.)
- 각 모델은 수치 결과 또는 명시적인 `unsupported` 이유를 남긴다.
- `metric3d_v2`, `unidepth_v2`, `unik3d`의 이전/현재 인코더 품질 차이를 측정한다.
- 평가 보고서는 JSON에서 자동 생성한다.
- 수동으로 골라낸 “좋아 보이는” 이미지만 보고 결론내리지 않는다.

## 5. P4 — fp16 대 fp32 직접 A/B

### 결과 — fp16 은 정확도에서 측정되지 않는다

같은 ONNX, 같은 빌드 옵션, 정밀도만 다른 엔진. 정확도는 DIODE 실내 50장 정답 데이터.

| model | AbsRel fp16 | AbsRel fp32 | 차이 | δ1 fp16 | δ1 fp32 | ms fp16 | ms fp32 | 비용 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `zipdepth` | 7.93% | 7.93% | −0.00p | 93.3% | 93.3% | 2.77 | 3.30 | **1.19×** |
| `moge_2` | 21.39% | 21.40% | +0.01p | 52.1% | 52.0% | 19.73 | 41.90 | **2.12×** |
| `depth_anything_ac` | 5.44% | 5.43% | −0.01p | 96.6% | 96.6% | 4.38 | 11.31 | **2.58×** |
| `depth_anything_v2` | 23.06% | 23.07% | +0.01p | 52.0% | 52.0% | 4.30 | 11.33 | **2.63×** |
| `distill_any_depth` | 5.96% | 5.95% | −0.00p | 95.9% | 95.9% | 4.32 | 11.38 | **2.63×** |
| `depth_pro` | 17.48% | 17.52% | +0.04p | 72.7% | 73.2% | 242.12 | 874.54 | **3.61×** |
| `depth_anything_v3` | 60.87% | 60.88% | +0.01p | 0.2% | 0.2% | 19.90 | 74.32 | **3.74×** |
| `metric_anything` | 15.63% | 15.67% | +0.04p | 75.4% | 75.1% | 67.00 | 304.05 | **4.54×** |

**여덟 모델 전부, 최대 차이 0.04%p.** 방향도 양쪽으로 갈리므로 부호에 의미가 없다.
AbsRel 5%~61%, 실행 시간 2.8ms~242ms 에 걸쳐 있는데도 정답 데이터가 정밀도를
구분하지 못한다. `depth_pro` 는 fp32 에서 δ1 이 오히려 0.5%p **떨어졌다**.

**이것이 이 저장소에서 fp16 을 쓰는 첫 번째 측정 근거다.** 기존 정확도 검증은
엔진과 그 엔진을 만든 ONNX 를 비교하므로, fp32 엔진과 fp16 엔진을 서로 다른 정답에
대해 똑같이 충실하다고 보고한다 — 정밀도 자체의 손해는 원리상 볼 수 없다.

### fp32 로는 빌드가 안 되는 모델이 둘 있다 — 빈 카드에서 재확인함

`unidepth_v2` 와 `unik3d` 는 672x896 fp32 에서 `build_serialized_network` 가 None 을
반환한다. 워크스페이스를 1 GiB 로 낮춰도 실패한다.

**한 번 의심했고, 확인했다.** 처음 실패했을 때 GPU 에는 잘린 ssh 명령이 남긴
프로세스들이 살아서 10 GB 를 전부 쥐고 있었다(아래 참조). 그렇다면 원인이 모델이
아니라 경합일 수 있으므로, 그것들을 정리하고 카드가 946 MiB 만 쓰는 상태에서
`unidepth_v2` 를 다시 빌드했다. **같은 실패다.** 모델이 맞다.

**이 둘에게 fp16 은 선택이 아니라 조건이다.** 성공으로 세지 않고 표에서 숨기지도
않는다.

### 운영 위험 — 잘린 원격 명령의 프로세스는 죽지 않는다

§13 규칙 2 는 "SSH 세션에서 분리한 프로세스가 살아남는다고 가정하지 않는다" 이고,
나는 이것을 "안 살아남을 수 있으니 확인하라" 로 읽었다. **실제 위험은 반대
방향이었다.**

P6 선별 중 배치가 네 번 잘렸다. 그때마다 ssh 는 돌아왔지만 데스크탑의 빌드는 계속
돌았고, 쌓여서 GPU 를 100% 사용률에 10,042 MiB 로 채웠다. 새로 띄운 `vggt` 빌드가
65분 동안 끝나지 않은 것도, fp32 빌드가 실패한 것처럼 보인 것도 그 위에서 일어난
일이다.

**원격 GPU 작업은 `schtasks` 로 띄운다.** 그래야 `schtasks /end` 로 확실히 끝낼 수
있고, 카드 상태(`nvidia-smi`)로 정리됐는지 확인할 수 있다. 측정 전에 카드가 비어
있는지 보는 것이 클럭을 고정하는 것만큼 중요하다 — 둘 다 "무엇을 재고 있는가" 에
대한 답이기 때문이다.

### 아키텍처가 비용을 정한다

`zipdepth` 의 **1.19배**가 눈에 띈다. 나머지는 2.1~4.5배인데 이 모델만 fp32 가
거의 공짜다. 저장소에서 유일한 컨볼루션 모델(6.1M)이고, 텐서코어보다 대역폭에
묶여 있어서 fp16 이 속도로 사줄 것이 적다. **이 모델에서는 정밀도 선택이 거의
무의미하고, `metric_anything` 에서는 4.5배짜리 결정이다.**

### 남은 것

`vggt` · `streamvggt` · `tr2m` 은 아직 fp32 엔진이 없다(정답 데이터 평가도 아직).
`metric3d_v2` 는 이미 fp32 라 비교 대상이 아니다.

### 원래 계획

### 범위

현재 fp16을 사용하는 모델마다 같은 ONNX와 빌드 옵션으로 fp32 엔진을 별도
생성한다. `metric3d_v2`는 현재 의도적으로 fp32이므로 새 fp32 비교 대상이 아니다.
따라서 신규 fp32 엔진은 최대 11개다. VRAM이나 TensorRT 제약으로 빌드할 수 없는
모델은 실패 원인을 기록하고 성공으로 세지 않는다.

### 비교

1. fp16 TensorRT 대 fp32 TensorRT — 정밀도 선택의 직접 영향
2. 두 엔진 각각 대 fp32 ONNX — TensorRT 변환 오차
3. 정답 데이터 지표 — 실제 품질 영향
4. latency, 엔진 크기, VRAM, fp32 fallback 비중

### 완료 조건

- 성공한 모든 모델에 동일 입력의 출력별 오차와 정답 데이터 지표가 있다.
- 속도만으로 fp16을 채택하지 않는다.
- fp32 엔진 빌드 실패와 평가 미지원 모델을 결과표에서 숨기지 않는다.
- 기본 엔진 변경은 별도 결정으로 남긴다.

## 6. P5 — 보류된 변경의 결정 게이트

### D2. uint8 입력 · **결정: 변이(variant)로 채택, 기준선은 유지**

정답 데이터로 판정할 수 있게 되어 채택 조건을 실제로 확인했다.

| 모델 | 입력 MB f32 → u8 | h2d ms | 총 ms | 속도 | AbsRel f16 → u8 | δ1 |
| --- | --- | --- | --- | ---: | --- | --- |
| `depth_anything_v2` | 3.22 → 0.80 | 1.034 → 0.269 | 4.29 → 3.40 | **−20.7%** | 23.06% → 23.07% (+0.01p) | 52.0% → 51.9% |
| `vggt` | 3.22 → 0.80 | 1.048 → 0.276 | 51.97 → 50.96 | −1.9% | 미측정 |  |
| `depth_pro` | 28.31 → 7.08 | 9.056 → 2.287 | 242.19 → 238.39 | −1.6% | 17.48% → 17.55% (+0.07p) | 72.7% → 72.7% |

**품질 저하는 fp16 대 fp32 와 같은 잡음 대역 안이다** (+0.01p, +0.07p).

**핵심은 절감이 비율이 아니라 절대량이라는 것이다.** 세 모델 모두 h2d 가 입력
크기에 비례해 줄었고 — PCIe 대역폭이지 모델의 성질이 아니다 — 남은 비율은 순전히
연산 시간이 얼마나 큰가로 정해진다. `depth_pro` 는 **절대 절감이 가장 크지만**
(6.8 ms) 242 ms 짜리 모델이라 1.6% 로 보이고, `depth_anything_v2` 는 절감이
0.77 ms 인데 4.3 ms 짜리라 21% 가 된다.

**결정**

1. **float32 NCHW 를 기준선으로 유지한다.** 비교표의 행들이 같은 입력 계약을
   가져야 하고, uint8 은 전처리 일부를 그래프 안으로 옮기므로 "모델의 속도" 에
   하네스의 선택이 섞인다.
2. **`depth_anything_v2` uint8 NHWC 를 명시적 변이로 추가한다.** 21% 를 공짜로
   얻고 품질은 잡음 안이다.
3. **느린 모델에는 적용하지 않는다.** `depth_pro` · `vggt` 는 2% 미만이라 입력
   계약을 바꿀 이유가 없다.
4. 판단 기준은 모델별로: **입력 MB × 약 0.24 ms/MB 가 연산 시간에 비해 큰가.**

### D3. 리사이즈 민감도 표 · **완료 — 1번(정답 데이터로 재측정), 도구 `tools/size_sweep.py`**

**기존 §5.7 표(`docs/model_contracts.md`)는 역사 기록으로 남긴다.** 기준선을 코드에서
재구성할 수 없는 이유가 분명해졌다: 그 표는 **모델 자신의 다른 크기 출력**을 기준으로
삼는다. 재현하려면 그때의 PyTorch 경로를 통째로 복원해야 한다.

**정답 데이터는 재구성이 필요 없다.** 그리고 두 방식은 서로 다른 답을 낸다 — 아래가
그 증거다.

#### `depth_anything_v2` — 큰 입력이 더 낫지 않다

DIODE 실내 50장. `tools/size_sweep.py`, `reports/tune/size_depth_anything_v2.json`.

| 크기 | ms | AbsRel | δ1 | 스케일 정렬 후 AbsRel | 정렬 후 δ1 | 맞춰진 배율 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **392x518** | **3.76** | 23.23% | 59.1% | **9.22%** | **91.7%** | **1.043** |
| 518x518 (발표) | 4.29 | 23.06% | 52.0% | 9.46% | 90.4% | 1.141 |
| 672x896 | 10.46 | **26.51%** | **38.7%** | 10.05% | 89.8% | **1.297** |

**형태는 거의 변하지 않는다** (정렬 후 AbsRel 9.22 → 10.05%, δ1 91.7 → 89.8%).
**움직이는 것은 스케일이다** — 1.043 → 1.141 → 1.297. 입력이 클수록 깊이를 더
짧게 본다.

**기존 표는 반대로 읽혔다.** §5.7 은 이 모델이 896x672 에서 AbsRel 2.1%, 518² 에서
9.8% 라고 적었다 — 518² 쪽이 나쁜 것처럼 보인다. 그 숫자는 **모델이 자기 자신과
얼마나 일치하는가**이지 맞는가가 아니다. 자기 일치도는 어느 쪽이 옳은지 말해주지
않는다.

#### 따라오는 사실 하나

**발표 중인 518x518 이 이 데이터셋에서 최선이 아니다.** 392x518 이 더 빠르고
(3.76 대 4.29 ms) 더 잘 보정돼 있으며(1.043 대 1.141) 형태 품질은 같다.

바꾸지는 않았다. 한 데이터셋, 한 종횡비(4:3)에서 나온 결과이고, 발표용 행을
바꾸는 것은 P5 의 다른 결정들과 같은 무게의 결정이다. **기록해 두고 다른 metric
모델들도 같은 스윕을 돌린 뒤 함께 판단한다.**

#### 다른 두 모델은 크기에 둔감하다 — 그리고 그 차이에 이유가 있다

| 모델 | 크기 | ms | AbsRel | 정렬 후 AbsRel | 맞춰진 배율 |
| --- | --- | ---: | ---: | ---: | ---: |
| `moge_2` | 336x448 | 19.39 | 20.91% | 9.37% | 1.213 |
| | 388x518 (발표) | 19.97 | 21.40% | 9.27% | 1.194 |
| | 476x630 | 21.20 | 21.69% | 9.24% | 1.219 |
| `metric_anything` | 336x448 | 66.78 | 15.76% | 6.10% | 1.125 |
| | 388x518 (발표) | 67.20 | 15.65% | 5.98% | 1.125 |
| | 476x630 | 68.19 | 16.42% | 6.12% | 1.123 |

**배율이 움직이지 않는다.** `moge_2` 는 1.194~1.219 안, `metric_anything` 은
1.123~1.125 안 — 후자는 세 크기에서 사실상 같은 값이다. `depth_anything_v2` 의
1.043 → 1.297 과 대비된다.

**순서에 이유가 있다. 카메라 기하를 이미지에서 추론할수록 크기에 민감하다.**

| 모델 | 스케일을 어떻게 얻는가 | 크기에 따른 배율 변동 |
| --- | --- | ---: |
| `metric_anything` · `moge_2` | **`metric_scale` 출력** — 예측한다 | 0.2% · 2% |
| `depth_anything_v2` | 이미지에서 직접 회귀 | **24%** |
| `unidepth_v2` · `unik3d` | **intrinsics 를 추론** | D11 의 3.1배 |

스케일을 따로 내놓는 모델은 입력 크기가 바뀌어도 그 값을 그대로 쓴다. 이미지의
겉보기 기하에서 스케일이 따라 나오는 모델은 입력을 늘리거나 줄이면 그 기하가 바뀐다.

#### 결정 — 발표용 행을 바꾸지 않는다

`depth_anything_v2` 는 392x518 에서 더 빠르고 더 잘 보정돼 있다. 그래도 바꾸지
않는다: **한 데이터셋, 한 종횡비(4:3), 실내에서만 나온 결과다.** 그 근거로 발표
숫자를 옮기는 것은 평가셋에 맞춰 튜닝하는 것이고, 이 저장소가 계속 피해 온 것이다.

`moge_2` 와 `metric_anything` 은 바꿀 이유 자체가 없다 — 어느 크기든 같다.

**남은 것:** 종횡비가 다른 평가 입력(P2 의 16:9·세로)이 생기면 이 스윕을 다시
돌린다. 그때도 392x518 이 나으면 근거가 하나가 아니라 둘이 된다.

#### 도구

`tools/size_sweep.py` 는 `tools/tune_build.py` 가 빌더 설정에 하는 일을 크기에 한다 — 엔진은
`engine/size/`, 결과는 `reports/tune/size_<model>.json`, **`reports/bench` 와
`reports/inputs` 에는 아무것도 쓰지 않는다.** 첫 시도가 정확히 그 규칙을 어겨서
발표용 행이 어느 엔진을 가리키는지 알 수 없게 됐었다.

크기 치환은 순수 텍스트라 `core/sizes.py` 에 있고 TensorRT 없이 테스트된다. 그
테스트가 저장소의 모든 export 스크립트를 패턴에 통과시킨다 — **패턴이 안 맞으면
원래 크기로 내보내고 "크기는 영향 없다" 는 결론이 나오기 때문이다.** `depth_pro` 는
`img_size` 를 로드된 모델에서 읽어 텍스트로 못 바꾸므로 이유와 함께 스윕 불가로
선언돼 있다.

없었으므로 경합이나 클럭 탓이 아니다.

### 세 가지 부정 결과 — 이것이 이 스윕이 낸 값이다

1. **레벨 5 는 일부 모델에서 폭발한다.** `streamvggt` **+131.1%**,
   `vggt` **+92.0%**, `moge_2` +16.1%, `unik3d` +14.3%. 뒤의 둘은 앞서 3회 독립 빌드로 확인한 불안정성이 그대로
   재현됐다. 우연이 아니라 성질이다. **`vggt` 는 이 스윕에서 가장 분명한 결과다** —
   105분을 더 탐색해서 2배 느린 엔진이 나왔다. `builder_optimization_level` 은
   "더 오래 찾으면 더 빠른 커널을 찾는다" 가 아니다. 탐색 공간이 넓어지면 큰
   트랜스포머에서는 나쁜 조합을 고를 수도 있다.
2. **`metric3d_v2` 는 양쪽 레벨에서 6~7% 느려진다.** 저장소의 유일한 fp32 엔진이고,
   더 깊게 탐색하는 것이 여기서는 일관되게 손해다.
3. **`tr2m` 레벨 4 는 2배 느려진다** (+99.9%). 입력이 둘인 유일한 모델이다.

### 레벨 0~2 는 측정하지 않았다 — 그리고 그 이유

계획서의 원안은 12모델 × 레벨 0~5 = 72빌드였다. 0~2 는 빼고 4·5 만 돌렸다.

근거: `moge_2` 를 0~5 전체로 돌린 기존 측정에서 레벨 0 이 +57.3%, 1 이 +3.0%,
2 가 +1.7% 로 전부 기본값보다 나빴다. 0~2 는 탐색을 *덜* 하는 설정이므로 기본값
3 을 이기려면 이례적이어야 한다.

**이 세 숫자에는 뒷받침하는 JSON 이 없다** (2026-08-14 감사). 원래 여기 적혀 있던
`reports/tune/moge2_*` 는 그 이름의 파일이 존재하지 않는다. 지금 남아 있는 것은
`reports/tune/opt_moge_2.json`(레벨 4·5)뿐이다. 규칙 7 대로라면 근거를 복구하거나
수치를 빼야 한다. **지우지 않고 여기 남기는 이유는, 이것이 레벨 0~2 를 빼기로 한
결정의 실제 근거였기 때문이다** — 근거가 약하다는 사실째로 남겨 두는 편이
결정만 남기는 것보다 정직하다.

**한 모델에서만, 그것도 재현할 수 없는 형태로 확인된 근거다.** 다른 모델에서 낮은
레벨이 이길 가능성을 배제하지 않으며, 여기 적어 두는 이유가 그것이다 — 빠뜨린
것이 아니라 뺀 것이다.

### 판정 — `streamvggt` 만 레벨 4, 나머지 13개는 기본 레벨 3

확인 실험(2026-08-14). `--repeats 3` 은 타이밍 캐시를 분리해 독립 빌드를 돌린다.
**양쪽 다 3빌드다** — 3빌드 평균을 단일 발표 엔진과 비교하면 비대칭이므로 분포 대
분포로 봤다.

| | 세 빌드 | 평균 |
| --- | --- | ---: |
| 레벨 3 (기본) | 53.30 · 53.43 · 54.03 | 53.58 ms |
| 레벨 4 | 52.10 · 52.28 · 52.69 | 52.36 ms |

**차이 -1.23 ms (-2.3%). 두 분포는 겹치지 않는다** —
레벨 3 의 가장 빠른 빌드(53.30)가 레벨 4 의 가장 느린 빌드(52.69)보다 느리다.

채택 조건 셋을 모두 통과했다: 평균 2% 이상 개선, 독립 빌드 3회, 분포 비겹침.

**이 실험에서 가장 중요한 숫자는 −2.3% 가 아니라 레벨 3 자신의 폭 0.73 ms
(1.4%) 다.** 클럭을 고정했는데도 같은 설정이 그만큼 흔들린다. 그
폭을 모른 채 단일 빌드 −2.3% 를 봤다면 채택할 근거가 없었다 — 선별 결과를 그대로
발표하지 않고 확인 단계를 둔 이유가 이것이다.

**나머지 13개는 기본 레벨 3 을 유지한다.** 문턱에 도달한 후보가 없었다.

### 레벨 4 는 그래프를 바꾸지 않는다 — 커널만 고른다

교체한 엔진을 다시 프로파일했다(2026-08-14). 옛 엔진의 프로파일을 새 엔진에
붙여 두지 않으려고 한 것인데, 그 김에 레벨이 무엇을 하는지가 보였다.

| | 레벨 3 | 레벨 4 |
| --- | ---: | ---: |
| 엔진 레이어 수 | 714 | **714** |
| fp32 시간 비중 | 4.08% | 4.13% |
| 이동 시간 비중 | 0.07% | 0.06% |
| 프로파일 총 시간 | 53.56 ms | 52.97 ms |
| 엔진 바이트 | 1,901,274,812 | 1,901,232,796 |

**레이어 수가 같고 fp32·이동 비중도 사실상 같다.** 이득은 그래프를 재구성해서
나온 것이 아니다 — fp32 폴백을 줄이지도, Reformat 을 없애지도 않았다. 같은 714개
레이어에 **다른 커널을 골랐을 뿐**이다.

**이것이 레벨 5 가 왜 폭발하는지도 설명한다.** 그래프가 같은데 두 배 느려졌다면
(`vggt` +92%, `streamvggt` +131%), 더 넓은 탐색이 더 나쁜 커널 조합을 고른 것이다.
구조 문제가 아니라 선택 문제다. `builder_optimization_level` 을 "더 오래 찾으면 더
좋다" 로 읽으면 안 되는 이유가 여기 있다.

### 네 번째 레벨 4 빌드가 분포를 넓혔다 — 실제 이득은 −0.96% 다

확인 실험 뒤 발표 엔진을 레벨 4 로 다시 빌드했더니 **52.83 ms** 가 나왔다.
확인 실험의 세 빌드(52.10 / 52.28 / 52.69) 어느 것보다도 느리다.

| | 값 |
| --- | --- |
| 레벨 4, 빌드 1~3 (확인) | 52.10 · 52.28 · 52.69 |
| 레벨 4, 빌드 4 (발표 엔진) | **52.83** |
| 레벨 3 세 빌드 | 53.30 · 53.43 · 54.03 |

**채택 판정은 유지된다** — 52.83 은 레벨 3 의 가장 빠른 빌드(53.30)보다 여전히
빠르고 두 분포는 겹치지 않는다. 그러나 **발표되는 이득은 확인 실험이 시사한
−2.3% 가 아니라 옛 발표 엔진(53.34) 대비 −0.96% 다.**

이것을 적어 두는 이유는 **3빌드로도 분포를 다 보지 못했다**는 사실이 이 스윕의
결론 중 하나이기 때문이다. 레벨 4 의 폭은 3빌드에서 0.59 ms 였고 4빌드에서
0.73 ms 로 늘어 레벨 3 의 폭과 같아졌다. 규칙 5 의 2% 문턱은 확인 실험의 평균
차이(−2.3%)로는 넘지만 발표 대 발표(−0.96%)로는 넘지 못한다 — **채택을 유지하는
근거는 평균 차이와 비겹침이지, 발표 표에 보이는 숫자가 아니다.**

## 9. 검증 자체를 검증한 결과 — 2026-08-14

이 절은 작업 항목이 아니라 사건 기록이다. **이 저장소가 "확인했다" 고 말할 때
무엇을 확인한 것이었는지에 대한 정정이다.**

### 테스트 240개가 실패할 수 없었다

12개 테스트 모듈이 pytest 이전에 쓰였다. 전부 같은 모양이다:

```python
_failures = []

def check(name, cond, detail=""):
    print(f"  {'PASS' if cond else 'FAIL'}  {name}...")
    if not cond:
        _failures.append(name)
```

`python tests/test_x.py` 로 돌리면 작동한다(맨 끝에서 `sys.exit`). **pytest 로
돌리면 작동하지 않는다** — 테스트 함수가 실패를 기록하고 정상 반환하므로 pytest 는
예외를 못 보고 통과시킨다. 합치면 **`pytest tests -q` 를 실패시킬 수 없는 검사
240개**이고, 이 저장소의 병합 검사가 바로 `pytest tests -q` 다.

**따라서 이 계획서와 커밋 로그에 있는 "테스트 통과" 중 기존 240개에 해당하는
부분은 아무것도 보증하지 않았다.** 새로 쓴 테스트(`test_gt`, `test_pointmap`,
`test_sizes`, `test_preprocess` 등)는 실제로 단언했고 실제로 실패했다 —
`depth_pro` 예외와 MoGe 솔버의 좁은 최솟값이 그렇게 잡혔다.

**해결은 `tests/conftest.py` 훅이다.** 240개 호출부를 assert 로 다시 쓰는 대신,
매 테스트 후 `_failures` 에 새로 들어온 것을 예외로 올린다. 40줄이고, **같은
모양으로 들어올 열세 번째 파일까지 막는다.** 모듈은 `check()` 와 `__main__`
러너를 유지한다 — 첫 실패에서 멈추지 않고 전부 보고하는 것이 그 파일들의 실제
장점이다. `tests/test_conftest_net.py` 가 옛 모양의 임시 모듈에 pytest 를 돌려
그물 자체를 검증한다.

### 실패·미측정도 레코드다 — 2026-08-14

서술로만 있던 "측정 안 됨" 을 JSON 레코드로 만들었다. 그것이 서술이었기 때문에
`PLAN.md` 가 12/14 를 14/14 라고 쓸 수 있었고, 사람이 디렉터리를 세어 보고서야
드러났다. 규칙 9 는 **삭제하지 않는다**였는데, 애초에 만들지 않은 것은 규칙이
덮지 않고 있었다.

`core/unmeasured.py` 가 형식이다. `status: "not_measured"` 하나로 식별하고,
`reason_code` 가 셋 중 무엇인지 말한다 — `not_run`(돌리면 된다) ·
`unsupported`(이 모델에서는 의미가 없다) · `different_contract`(먼저 만들어야
할 것이 있다). "숫자가 없다" 는 이 셋을 하나로 뭉개고 있었고, `zipdepth`(돌려라)
와 `vggt`(돌리지 마라)가 같은 빈칸으로 읽혔다.

| 어디 | 누가 | 왜 |
| --- | --- | --- |
| `reports/accuracy.json` | `zipdepth` · `tr2m` | `not_run`. 엔진·ONNX·입력 텐서가 다 있다. `tr2m` 의 두 번째 입력도 `reports/inputs/tr2m__text_features.npy` 로 이미 커밋돼 있다 |
| `reports/profile/tr2m.json` | `tr2m` | `different_contract`. `tools/profile_model.py` 는 binding 0 만 채운다. 두 번째 binding 을 비운 채 잰 시간은 아무도 돌리지 않은 계산의 프로필이다 |
| `reports/gt/vggt.json` · `streamvggt.json` | `vggt` · `streamvggt` | `unsupported`. 출력이 정규화 좌표라 미터가 아니다. 이 표에서 채점하면 빠진 단위를 오차로 보고하게 된다. 이 둘에 대해 정의된 측정은 `--scale-only` 쪽이다 |
| `reports/gt/tr2m.json` | `tr2m` | `different_contract`. 이미지마다 프롬프트가 필요하고 그 계약이 아직 없다(`model_contracts.md` 「`tr2m` 평가 계약」) |

**2026-08-14 후속 상태:** 앞의 표는 미측정을 처음 기록했을 때의 상태다.
`zipdepth`·`tr2m` 엔진 정확도는 전수 재실행으로 14/14가 됐다. tr2m 프로파일은
첫 시도가 두 번째 입력을 비운 무효 측정임을 확인한 뒤, `profile_model.py`가
`tr2m__text_features.npy`까지 바인딩하도록 고쳐 다시 측정했다(369/369 레이어).
vggt·streamvggt는 일반 미터 표에서는 계속 `unsupported`이고, 대신
`reports/gt_scale_only.md`에서 각 50장을 측정했다. tr2m GT 계약만 남아 있다.

생성기 셋이 그 레코드를 읽어 표시한다. `compare.py` 는 `fp32`·`moved` 칸을
`-` 대신 `not measured` 로 쓰고 「Layer profiles not measured」 절을 붙인다.
`verify_accuracy.py` 와 `evaluate_gt.py` 는 「Not measured」 절을 이유 코드별로
묶어 낸다. **점수는 하나도 움직이지 않았다.**

`tests/test_unmeasured.py` 가 두 가지를 건다: 모델 14개가 결과 셋 셋 곳에서
전부 설명되는가(숫자 아니면 레코드), 그리고 **발표된 마크다운이 실제로 그
이름과 이유를 말하는가.** 두 번째가 중요하다 — 기존 회귀 테스트는 생성기를
자기가 쓴 파일과 비교하므로, 생성기가 레코드를 빠뜨리고 파일도 안 적으면 둘이
완벽하게 일치한다. 규칙 11 대로 9가지 방법으로 일부러 깨뜨려 전부 빨간불을
확인했다(레코드 삭제, 이유 코드 개명, 레코드에 점수 삽입, 발표 파일에서 절
제거, 칸을 `-` 로 되돌리기, 없는 모델 이름, 파일명과 `model` 필드 불일치,
그리고 생성기 자체에서 절 출력 코드 제거).
